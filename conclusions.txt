SHOPPINGCART E2E AUTOMATION - CONCLUSIONS
=========================================

Repository: https://github.com/odmarinm/ShoppingCart
Site under test: http://opencart.abstracta.us/ (public OpenCart demo store, shared server)


1. SUMMARY
----------
An end-to-end (E2E) automated test was built for the purchase flow of the OpenCart demo store:

  - Add two products to the cart
  - View the shopping cart
  - Complete the checkout as a guest ("Guest Checkout")
  - Confirm the order up to the message "Your order has been placed!"

Current suite: 1 feature, 2 scenarios (Scenario Outline with 2 examples), 16 steps - all passing.
The suite was run several times in a row with stable results. Each run places 2 real orders
on the demo store.


2. TECHNOLOGIES
---------------
- Python 3.11+ (developed and tested with Python 3.15)
- Behave 1.3.3 ............ BDD framework, scenarios written in Gherkin
- Playwright 1.65.2 ....... browser automation (Chromium by default; Firefox, WebKit, Edge, Chrome)
- allure-behave 2.16.2 .... Allure results generated by Behave
- python-dotenv 1.2.4 ..... configuration from a .env file
- Allure CLI 2.x + Java ... HTML report (optional: tests run without it)
- Git + GitHub ............ version control

Why Playwright
--------------
- Auto-waiting: every action waits for the element to be visible, enabled and stable. That matters
  here because the checkout is a single page whose 6 steps are loaded by AJAX.
- Web-first assertions (expect) that retry until a condition is met or the timeout expires, with
  no fixed sleeps anywhere in the code.
- Traces: one .zip per scenario with screenshots, DOM snapshots, network and console of every
  action, the best tool to analyze a failure that cannot be reproduced locally.
- One isolated browser context per scenario (own cookies = own cart) in milliseconds.
- The browser is downloaded by Playwright itself (no WebDriver/driver version management), and an
  installed Edge or Chrome can be used instead with one setting (BROWSER_CHANNEL).


3. ARCHITECTURE
---------------
Same structure and conventions as the PetStore API project (Behave + Allure), with the HTTP layer
replaced by a Page Object Model.

Layer rule: features -> steps -> interactors -> pages. Only src/pages uses Playwright.

  features/      Gherkin .feature files, grouped by business area (features/checkout/)
  steps/         One file per area: catalog_steps, cart_steps, checkout_steps
                 When performs actions and stores what was read, Then validates
  interactors/   Use cases called by the steps (ShoppingInteractor): combine the pages
  pages/         Page Object Model, the only layer that talks to the browser:
                   BasePage ........... navigation, header (search, cart button), alerts
                   CatalogPage ........ home page and search results
                   ProductPage ........ price, 'Ex Tax' price, quantity, "Add to Cart"
                   CartPage ........... product rows and totals of the cart
                   CheckoutPage ....... the 6 checkout steps
                   OrderSuccessPage ... "Your order has been placed!"
  models/        Data read from the pages (AddedProduct, CartSummary, CartLine, OrderResult...)
  builders/      Test data (GuestCustomerBuilder), never touch the browser
  validators/    Validations of the data read, no Playwright (cart_validator, order_validator)
  enums/         Route, CheckoutOption, PaymentMethod, StoreMessage, Browser, TracingMode
  config/        Settings loaded from .env
  utils/         Money parsing (Decimal), assertions, Allure Checker

Design decisions:
- Pages return data (models) and never validate; validators never touch the browser. This keeps
  the page objects reusable for any other scenario (e.g. negative tests).
- ONE consolidated validation step per business result ("the shopping cart contains the added
  products", "the order has been placed successfully") instead of many small steps.
- All the checks of a validation run, and a failure lists every value that did not match.
- Amounts are compared as Decimal, never as float, to avoid rounding errors.
- Products are found like a real user does: search box -> exact name in the results -> product
  page (no hardcoded product ids or URLs).
- Each scenario uses a new browser context: it always starts with an empty cart and does not
  depend on the order or the result of other scenarios.
- Unique e-mail per run for the guest, because the store is shared.
- No fixed waits (sleep): every wait is for a concrete condition (element visible, header cart text
  changed, URL of the success page, region list loaded, no AJAX request in progress).


4. SCENARIOS
------------
guest_checkout.feature (tags @checkout @guest_checkout)

  Scenario Outline: Buy two products as a guest
    Example 1: 1 x MacBook + 1 x iPhone
               Guest: Ana Lopez - Bogota D.C., Colombia - Bank Transfer
    Example 2: 1 x Samsung SyncMaster 941BW + 2 x Nikon D300
               Guest: Carlos Perez - Greater London, United Kingdom - Cash On Delivery

The two examples were chosen on purpose: Colombia has no taxes configured in the store and the
United Kingdom has VAT and Eco Tax, so both tax paths and both payment methods are covered.
Example 2 also uses a quantity other than 1.


5. VALIDATIONS PERFORMED
------------------------
a) Products added (after "Add to Cart"):
   - Success message of each product: "Success: You have added <product> to your shopping cart!"
   - Header cart button: number of items = sum of quantities, amount = sum of price x quantity

b) Shopping cart:
   - Number of product rows = number of products added
   - For each product: quantity, unit price = price shown on the product page,
     line total = unit price x quantity
   - Sub-Total = sum of the 'Ex Tax' prices x quantity (read on each product page)
   - Total = Sub-Total + every other row (Eco Tax, VAT...)
   - Total = sum of the product line totals
   - Header cart button = number of items and Total of the cart
   - Any store warning (e.g. out of stock) is shown in the report as information

c) Confirmed order (Step 6 "Confirm Order", before clicking "Confirm Order"):
   - Same products and quantities as the cart
   - Line total = unit price x quantity
   - Sub-Total = sum of the 'Ex Tax' prices x quantity
   - Total = Sub-Total + shipping + taxes
   - At least one delivery method is offered

d) Order confirmation page:
   - URL contains route=checkout/success
   - Heading = "Your order has been placed!"
   - Message "Your order has been successfully processed!" is shown
   - Header cart is empty: "0 item(s) - $0.00"


6. ALLURE REPORT AND EVIDENCE
-----------------------------
- Each scenario shows its Gherkin steps, with the page actions as sub-steps, for example:
    Add 2 x 'Nikon D300' to the cart
      Search the catalog for 'Nikon D300'
      Open the product 'Nikon D300' from the results
      Set quantity to 2
      Click 'Add to Cart'
- A full-page screenshot is attached to EVERY step. When a step fails, the screenshot is named
  "Screenshot on failure" and the page URL and HTML are attached too.
- Each check is a sub-step with the expected and actual values:
    ✔ Total (= Sub-Total $601.00 + Flat Shipping Rate $5.00): expected $606.00 | got $606.00
    ✘ ... (red when it fails; its group turns red too)
    ℹ Warning shown by the store: ... (information, never fails)
- The Playwright trace (.zip) of each scenario is attached to the report and saved in
  reports/traces (open with "playwright show-trace" or https://trace.playwright.dev).
- Optional video per scenario (RECORD_VIDEO=true).
- The "Environment" widget shows Base URL, browser and version, headless, Playwright, Python and OS.
- reports/allure-results is cleared at the start of each run, and the HTML report is regenerated
  automatically at the end. Open it with: allure open reports/allure-report


7. FINDINGS ON THE SITE UNDER TEST
----------------------------------
Defects / inconsistencies:
- The heading of the shopping cart page is wrong: it shows "Use Gift Certificate (10.00kg)"
  instead of "Shopping Cart" (the browser tab and the breadcrumb do say "Shopping Cart").
  A wrong language string. It is reported in this document and NOT asserted, so that a known
  cosmetic defect does not block the purchase flow test.
- The products used are marked with "***" in the cart with the warning "Products marked with ***
  are not available in the desired quantity or not in stock!", but the store still allows
  completing the order. Either stock checkout is intentionally allowed in this demo, or orders
  can be placed for products that cannot be delivered. The warning is shown in the report.
- The store mixes HTTP and HTTPS with explicit ports: the site opens on http://...:80 but the
  "Checkout" button and the account links go to https://...:443. It works, but the session
  moves between protocols in the middle of the purchase.
- Session race condition in the checkout: OpenCart saves the session without locking, so when two
  AJAX requests run at the same time, the one that finishes last overwrites what the other saved.
  Observed in a run: the delivery address form fires "checkout/checkout/country" at the same time
  as "shipping_method/save"; the country request finished later and erased the delivery method
  from the session. After "Confirm Order" was requested, the store silently sent the checkout back
  to Step 1, with no error message. A fast user (or a slow network) can hit this as well.
- Changing the quantity on the product page fires an AJAX call (getRecurringDescription) whose
  response removes EVERY alert of the page. If it answers after "Add to Cart", it erases the
  "Success: You have added ..." message: the product is added but the user gets no confirmation.
- Shipping is charged Eco Tax and VAT: for the United Kingdom, the $5.00 flat shipping adds
  $2.00 of Eco Tax and $1.00 of VAT (Eco Tax goes from $6.00 in the cart to $8.00 in the order
  for the same 3 products). Probably a configuration of the demo (shipping with the "Taxable
  Goods" class), but an Eco Tax on shipping is unusual and worth confirming with the business.

Behaviors that affect the test design:
- The cart and the product page show prices WITH taxes of the store's default address
  (United Kingdom). The taxes are recalculated with the guest billing address in the checkout:
  the cart total was $725.20 and the confirmed order for Colombia was $606.00 (no VAT, no Eco
  Tax, + $5.00 shipping). Therefore the cart Total can NOT be compared with the order Total;
  instead the Sub-Total (always without taxes) is validated against the 'Ex Tax' prices, and the
  arithmetic of each totals table is validated. The difference is shown as information.
- In the confirm step, the unit prices include taxes when the address has taxes (UK) and do not
  when it has none (Colombia), while the Sub-Total never includes them.
- Searching "MacBook" returns "MacBook", "MacBook Air" and "MacBook Pro": the product is chosen
  by EXACT name, not by "contains".
- The header cart button is refreshed by JavaScript a moment after "Add to Cart": the test waits
  for its text to change before going on.
- The list of regions is loaded by AJAX when the billing form opens (default country) and again
  after choosing the country, and every reload resets the selected region: the test waits for
  all those requests before selecting the region.
- The checkout is a single page with 6 accordion steps loaded by AJAX. Step 3 (Delivery Details)
  is skipped because "My delivery and billing addresses are the same" is checked by default.
- The demo server is slow: some actions take more than 5 seconds and a checkout takes 15-20
  seconds. Playwright's expect() uses its own 5-second timeout by default, which made the first
  runs fail intermittently; it is now aligned with the global timeout (TIMEOUT=45 s in .env).
- Every run creates real orders on a public, shared store.


8. RELIABILITY
--------------
- No fixed sleeps: only waits for concrete conditions (auto-waiting + web-first assertions).
- Before every action that saves data (Add to Cart, each checkout "Continue", Confirm Order) and
  after choosing the country, the test waits until jQuery has no AJAX requests in progress
  (jQuery.active === 0). This avoids the two race conditions described in section 7, which made
  the suite fail intermittently ("Please select a region / state!", checkout back to Step 1,
  missing success message). After this change the suite passed 6 runs in a row.
- After selecting the region, the test checks that it is really selected, because every reload
  of the region list resets it.
- If the checkout goes back to Step 1, the error says so explicitly.
- One timeout for actions, navigation and expect(), configurable in .env.
- If a checkout step does not open, the error message includes the validation errors shown by
  the store (e.g. a required field), instead of a generic timeout.
- Isolated browser context per scenario: no shared cart, cookies or session.
- Unique guest e-mail per run.
- Evidence on every step (screenshot) and per scenario (trace), so a failure in CI can be
  analyzed without running it again.


9. POSSIBLE IMPROVEMENTS
------------------------
- Negative scenarios with the same page objects: required fields empty in the billing details,
  Terms & Conditions not accepted, invalid e-mail.
- Validate the order in the store admin (or by e-mail) to confirm it was actually saved.
- Run in parallel (one browser context per worker) and in several browsers in CI
  (e.g. GitHub Actions with the Allure report as an artifact).
- Visual comparison of key pages (cart, confirmation) to detect defects like the cart heading.


10. HOW TO RUN (short version - see README.txt for details)
----------------------------------------------------------
  git clone https://github.com/odmarinm/ShoppingCart.git
  cd ShoppingCart
  python -m venv .venv
  .\.venv\Scripts\pip install -r requirements.txt               (macOS/Linux: .venv/bin/pip ...)
  .\.venv\Scripts\python -m playwright install chromium         (macOS/Linux: .venv/bin/python ...)
  copy .env.example .env                                         (macOS/Linux: cp ...)
  .\.venv\Scripts\behave                                         (or --tags=@guest_checkout)
  allure open reports/allure-report
